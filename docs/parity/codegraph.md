## Scope and comparison rules

- Stage 1 serves committed-snapshot facts through PostgreSQL, shared Go query services, REST/MCP, and the GraphNest browser. Source-dependent analysis reads the exact indexed commit. CodeGraph runs only in the reference harness; it is not a server runtime dependency.
- Stage 2 imports existing CodeGraph databases read-only, without re-indexing by default. Stage 3 owns local indexing, working-tree source, watchers, installation, agent integration, and offline workflows in a GraphNest-owned data location.
- The fixture/task column names a stable acceptance task. `planned:<id>` means the runnable fixture/query does not yet exist; it must not be skipped and reported as a passing parity test. One source fixture may cover several tasks, but each assertion remains independently identifiable.
- `facts` comparison means canonical entity/edge sets including original direction, separate occurrences, missing values, metadata, and producer identity. `answer` means required relevant facts within the requested budget, verbatim source, evidence, ordering where significant, and completeness. `schema` means discovery, defaults, required arguments, rejection, and authorization behavior. `workflow` means API result plus browser/CLI interaction and observable error states. Ranking need not reproduce incidental timestamps or console styling, but cannot lose required answers within the tested budget.
- Source references below are paths at the pinned commit. Test references establish useful oracle cases; the acceptance task still requires a GraphNest-side assertion. Synthetic schema records establish transport coverage only; they never count as producer extraction or language/framework parity.
- Preserve existing GraphNest managed enrichment and SCIP compatibility. No other analyzer is an input or a new dependency in this initiative. GraphNest numeric relationship values must retain their existing identities rather than adopt CodeGraph array positions.

## Release gates and performance

The current runnable reference fixture is `polyglot-core` under `test/fixtures/codegraph/`. Its `manifest.json` is authoritative for real emitted kind/relation coverage, producer/runtime/configuration and source hashes. `expected.json` contains real producer answers; `ts-call-normalize` independently requires the `greet` → `normalize` call. `synthetic-contract.json` separately covers all vocabulary values; it does not claim all values are emitted by this producer configuration. Run `make parity-reference` for offline validation; use the live regeneration command recorded in the execution record and `test/parity/generate_reference.py --help` for the pinned producer run. Missing emitted kinds/relations must stay visible even when vocabulary validation passes. The current portable run emits **20/23 node kinds and 9/13 relationship kinds**. Missing node kinds are `protocol`, `parameter`, `export`; missing relationship kinds are `exports`, `type_of`, `returns`, `overrides`. Source inspection found no explicit emission sites for those four relationship kinds in the TypeScript extraction/resolution implementation; this is not proof that no producer path can ever emit them. Preserve all values when present in an input database. Ruby module and Java namespace source fixtures exercise two additional kinds; `unicode.ts` carries CRLF and accented/astral source content for subsequent coordinate-conversion assertions.

Correctness gates are zero silently dropped kinds/relations/occurrences/metadata, no cross-repository disclosure (including counts and paths), exact-source context, bounded responses, and explicit partial/unresolved/truncated status. Each planned task above and below must gain an executable oracle comparison before its owning stage passes. Existing GraphNest unit success does not substitute for these comparisons.

Performance baselines must record machine/OS/runtime, producer/source/config hashes, graph counts, database/artifact sizes, peak RSS, and warm/cold conditions. Required workloads: full reference generation, import validation and publication, exact/name/filtered search, callers/callees, bounded fanout traversal, explore with source, impact/affected tests, map/screens/steps, and browser first useful render. Capture at least five measured runs after warm-up and retain median and p95; report timeouts as failures, not omitted samples.

The accepted roadmap freezes these proposed starting gates: preserve existing GraphNest warm-query p95 within **10%** of its baseline, and keep GraphNest-local warm-query p95 within **1.25x** pinned CodeGraph on the same tasks.
